# 154 迁移分析：卡点、已量化的进度与下一步

**结论先说：154 原版已固化，定制增量和 139 → 154 符号映射已自动推导并量化；
但 68 个改动文件里的 78 处注入点还不能全部可靠落位，因此本次没有把
`decompiled/` 切成 154 —— 半迁移的 APK 会“能装能开、功能悄悄失效”，比不升级更糟。**

139 是同一个 APK 家族的上一个版本（`26.11.05.d5c365e`）。两次发布的原始工程没有
R8 映射文件可用，而 139 里我们的定制直接写在**混淆后的类**上，所以升级的本质是：
把“在旧混淆名上的补丁”翻译成“在新混淆名上的等价补丁”。

## 为什么不能机械套用

1. **类名/成员名整体轮换。** 8,344 个 139 类中只有 355 个在 154 里同名同内容；
   同名但内容不同的是 7,967 个（例如 139 的 `Ldv;` 是设置项助手，154 的 `Ldv;` 是别的东西）。
   `dv`、`jc0`、`wb0`、`yb0`、`f55`、`qm5` 这些定制依赖的类，名字在 154 里全部指向别的类。
2. **代码本身也变了。** 唯一化方法体比对（占 139 全部类的 54.8%）可确认 4,572 个类；
   其余类的代码在 154 里有增删、内联或重构。
3. **Compose 版本回退**（1.13.0-alpha01 → 1.12.1），编辑器/设置页那批 Compose 大函数
   （`bf0`、`em5`、`hl`、`vt0`、`si3`、`ru5`…）的指令序列变化明显，靠 k-gram 对不齐。
4. **资源 ID 位移**：154 新字符串占了 139 定制字符串用过的 `0x7f0f0508+` 号段，
   定制字符串必须按 `public.xml` 的 `(type,name)` 重新编号。

## 已完成的量化结果

### 定制增量（`inventory.json`）

| 项目 | 数量 |
|---|---|
| 改动文件 | 68（62 个 smali + `AndroidManifest.xml` + 4 个 `strings.xml` + `public.xml`） |
| 新增文件 | 1,362（1,355 smali + 7 个 asset） |
| 被改方法 | 78（27 个只改 `Toast → FToast`，51 个是真实注入） |
| 加字段的类 | 2（`f55` 加枚举常量 `t`，`qm5` 加 `cfgD:Z`） |
| 删除 | 0 |

### 符号映射（`symbol-map.json`）

- 8,344 个 139 类中映射出 **4,596 个（55.1%）**：4,564 个由“两版都唯一”的方法体锚定，
  32 个由结构+字面量/资源引用证据补足；74 个出现“一目标多来源”的冲突，按证据强度取其一并把其余降级为未定，不猜。
- 定制真正依赖的 **113 个类**里映射出 **97 个**，未解决 16 个：
  `a55 ag7 ci3 dj3 em5 iw4 jh2 jx4 ne3 p51 pr si3 vt0 yk6 yt z11`。
- 成员级映射 **2,269 条**（同一类对内按调用序列对齐投票得到，仅覆盖定制依赖的类）。

### 定制代码的可移植性（`dry-run.json`）

用该映射把 1,355 个自写 smali 逐个重写并检查悬空符号：

- **1,339 个（98.8%）可以完全重写**，引用全部落在 154 上；
- 剩 16 个文件（`CfgGlue/CfgNav/CfgIcon/CfgDefer/AppPerm/…` 这些手写胶水）还有 **26 条**成员引用待确认，
  例如 `Lt72;->T(IZ)Z`（Compose `ComposerImpl` 的方法）、`Lqm5;->m(Ljava/lang/String;)V`。

也就是说：**自写代码的迁移接近可自动化，真正的卡点集中在 78 处注入点。**

### 注入点落位（`port-sites.json`）

用“只看跨类调用序列”（忽略寄存器/控制流抖动）的方式在 154 里定位每个被改方法：

| 覆盖率 | 数量 | 含义 |
|---|---|---|
| ≥ 0.8 | 29 | 落点基本确定 |
| 0.5 – 0.8 | 32 | 需要人工确认 |
| < 0.5 | 17 | Compose 大函数重构，需按语义重找 |

另有 **59/78** 的候选与类映射一致（`consistentWithClassMap`）；两者同时成立的是 25 处。
典型已确认的例子：`dv.b(ZZZ)V → mu.b(ZZZ)V`、`f55.<clinit> → ab5.<clinit>`（枚举常量串完全一致）、
`jc0.g()Lwb0; → gc0.g()Ltb0;`、`w70 拷贝方法 → tb0.a(...)`。

## 下一步（可执行清单）

1. **补齐 16 个未解决类**。其中 `pr`、`em5`、`si3`、`ru5`、`yt`、`ci3` 都是 Compose 大函数/字符串助手，
   建议先定 `z11`（`Composer` 接口，0 成员）和 `t62/t72/p62` 这组 Compose 基础类型，
   再用它们的调用点反推宿主类。
2. **把 78 处注入点分成三批处理**：29 处高置信（可直接搬 + 复核）、32 处中置信（对调用序列人工确认）、
   17 处低置信（按功能语义在 154 里重找锚点，必要时重写为等价注入）。
3. **资源迁移**：12 个定制字符串按 `(type,name)` 重新编号到 154 `public.xml` 尾部
   （154 的 `string` 最大 ID 是 `0x7f0f0538`，定制从 `0x7f0f0539` 起追加），同步 4 个语言的 `strings.xml`；
   Manifest 增量（3 个权限、`BoxVpnService`、`BootReceiver`、4 个 Activity）按名字直接合并。
4. **构建与回归**：`scripts/check_smali_references.py` + `bash scripts/build.sh`；
   然后把 `inventory.json` 提升为 `full.json` 形式的哈希固定计划，接回 `scripts/migrate_upstream.py`。
5. **真机验收**：root/非 root、VPN 授权、常驻/开机自启、核心切换、编辑器面板。

## 为什么不直接“先切过去再说”

- 27 个 Toast 补丁可以全量替换（`Landroid/widget/Toast;->makeText` 在 154 还剩 58 处），
  但真实注入点是“设置项过滤、模式枚举、编辑器顶栏、配置历史、电池优化入口”等，
  位置错了不会编译报错，只会**运行时不生效或崩溃**。
- 154 的类名与 139 大量同名异义，任何“按名字对齐”的自动改写都会静默写坏代码；
  项目内部引用检查（`check_smali_references.py`）只能发现“引用不存在”，发现不了“引用到别的类”。

因此本仓库的约定是：**映射必须有证据、补丁落点必须可复核，才允许进 `decompiled/`。**
